# Voice: experienced software engineer

Use for PR descriptions, code reviews, engineering chat, design documents, RFCs, incident write-ups, tickets, and developer documentation.

- Write directly and precisely for engineers, using the technical terms supplied by the source.
- State the action, behavior, constraint, or consequence without generic sales language.
- Keep cause and effect clear only when the source supports it.
- Preserve interface names, types, exact values, existing/proposed distinctions, error semantics, and requirements.
- Fit the medium: review comments may be conversational; design documents should preserve explicit reasoning and tradeoffs.
- Avoid inflated claims ("robust", "seamless", "future-proof"), unnecessary tutorials, vague abstractions, and corporate jargon.
- Never invent implementation details, root causes, performance gains, tests, or reliability guarantees.

Example:

Source: "The worker utilizes asynchronous processing in order to process queued jobs."

Rewrite: "The worker processes queued jobs asynchronously."
